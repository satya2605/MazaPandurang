# Maza Pandurang — Final Software Requirements Specification

**Document Version:** SRS v1.0  
**Project:** Maza Pandurang  
**Platform:** Flutter Mobile + Web Admin/Stakeholder Dashboard  
**Backend:** Node.js + TypeScript  
**Database:** Supabase PostgreSQL + PostGIS  
**Target:** Functional Varithon/Buildathon MVP  
**Development Constraint:** Approximately 2 days for the functional demonstration

---

# 1. Document Purpose

This SRS defines the final system that the development team should build for **Maza Pandurang**, a Wari-focused digital platform intended to centralize navigation, essential services, Palkhi/Dindi information, emergency assistance, city guidance and multilingual AI assistance.

The original Varithon proposal describes Maza Pandurang as a multilingual, voice-first platform combining AI assistance, service discovery, live navigation, Dindi management, Palkhi tracking and city guidance for Warkaris, Dindi leaders, NGOs, healthcare teams, police and local citizens. 

The original problem is fragmentation of information about food, water, toilets, medical camps, accommodation, traffic and emergency services, particularly affecting elderly and first-time pilgrims. 

This document converts that concept, together with the decisions made during requirements clarification, into an **implementation-ready specification**.

---

# 2. Product Vision

## 2.1 Vision

> **Maza Pandurang is a unified digital companion for the Wari that helps pilgrims find essential services, navigate safely, stay informed about the Palkhi and Dindi, access emergency assistance, and obtain Wari-specific information through a simple multilingual interface.**

The application should prioritize:

- simplicity
- accessibility
- location awareness
- reliable information
- safety
- multilingual interaction
- minimal interaction complexity

The original proposal specifically identifies elderly and first-time Warkaris as important users and highlights their difficulty with conventional digital applications and navigation tools.

17. Role-based stakeholder dashboards
18. Offline caching of critical information
19. Bhakti section

---

# 4. Out of Scope for MVP

The following must **not delay the core demonstration**:

- AI ambulance dispatch
- AI crowd-density prediction
- IoT water/sanitation monitoring
- Bluetooth mesh networking
- smart Darshan prediction
- full autonomous emergency dispatch
- community social feed
- large-scale analytics
- complete offline map navigation
- custom turn-by-turn navigation engine
- expansion to other pilgrimages

The original proposal itself places AI ambulance dispatch, crowd heatmaps, IoT monitoring, Bluetooth mesh, offline devotional content and Darshan prediction under future scope.

# 7. Authentication Model

## 7.1 Public access

Users do **not** need an account to:

- open the application
- view the map
- view public service locations
- search services
- view Palkhi information
- view public Dindi information
- view traffic information
- use the city guide
- use basic Tilak functionality
- open Google Maps navigation
- view Bhakti content
- report incorrect service information

This is intentional. Requiring registration for basic service discovery would work against the project's accessibility goal.

# 12. Database

## Decision

> **Supabase PostgreSQL + PostGIS**

This replaces the original Firebase database proposal for the actual implementation.

The original PDF lists Firebase among proposed technologies, but it does not require Firebase specifically; the architecture requires a centralized cloud backend, realtime information and offline capability. 

Supabase is preferable for the finalized system because the application contains substantial relational and geographic data.

# 45. Tilak AI

## Identity

Tilak is the Wari-specific AI assistant for Maza Pandurang.

The original proposal describes Tilak as a multilingual voice assistant supporting nearby services, emergency guidance and live pilgrimage information. 

---

# 46. Tilak Scope Restriction

Tilak answers only **Wari-related questions**.

Allowed:

- Wari
- Palkhi
- Dindi
- Wari routes
- Wari services
- medical camps
- food/water/toilets
- traffic
- Wari-related city information
- temples/heritage relevant to the pilgrimage
- emergency guidance
- application functionality

Not allowed as general-purpose assistant:

- coding
- general academic questions
- unrelated politics
- unrelated entertainment
- unrelated general knowledge

Response:

> "I can help only with Wari-related information."

---

# 47. Tilak Memory

Tilak must **not maintain persistent conversation memory**.

No:

- user conversation history
- personal AI memory
- long-term conversation profile

Each request is independent.

Temporary request context is allowed when necessary for executing a current action.

# 82. Role-Based Access Control

Example:

A Dindi leader attempts:

```text

```

```text

 ↓
```

# 83. Location Privacy

Location data is sensitive.

Requirements:

- explicit consent
- minimum necessary collection
- no public member-location sharing
- no unnecessary location history
- authorized access only
- ability to disable sharing

# 84. AI Security

AI must not be trusted with authorization.

The LLM cannot decide:

> "This user is an admin."

Node.js decides.

Similarly, AI cannot directly execute:

```text
DELETE service
APPROVE NGO
PUBLISH traffic
CHANGE PALKHI
SEND emergency
```

without backend authorization.

# 103. Final Product Principle

The most important architectural rule for this project is:

> **AI should enhance the application, not control it.**

The actual system of record is:

```text
Supabase
     ↑
Node.js
     ↑
Flutter
```

Tilak sits on top of that system:

```text
                   Tilak
                     ↓
               AI Tool Gateway
                     ↓
                Node.js APIs
                     ↓
                Verified data
```

Therefore, if Gemini is down, OpenAI is down, Sarvam is down, or the AI subsystem completely fails, users can still:

- find a medical camp
- view services
- view the Palkhi
- view their Dindi
- see traffic
- request emergency assistance
- access the map
- navigate
- receive safety notifications

That is the correct architecture for a safety-oriented Wari application.

The original proposal's central objective is to bring fragmented Wari services, navigation, communication and information into one location-aware ecosystem.  This SRS preserves that objective while restricting the two-day implementation to features that can actually be made functional and demonstrated reliably.
